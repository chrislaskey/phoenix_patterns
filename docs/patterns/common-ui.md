# Common UI

Enforce the use of a the design system for all common elements, while still
allowing for custom components.

## Overview

UI drift is a real and recurring problem in web applications. This pattern works
by finding a healthy balance between enforcement while still being flexible.

It works by treating the CoreComponents file generated by Phoenix as the design system
for the application. If a public function is defined in it, like `def button` then custom
checks ensure that all references to `<button />` in the application call the
CoreComponent definition.

Add a new public function to the module and it will be enforced automatically
as well.

Customization is important, and there are two ways to write custom code:

- Anything not in CoreComponents is allowed (e.g. `<div />`) 
- Create a custom component (e.g. `<button />` can become `<Custom.button />` where `Custom.button` calls CoreComponents `button` with extra attributes added).

This allows individual features to still customize output, without requiring
everything to be defined in CoreComponents.

Note: The config can be used to define a custom component module name and path. It also supports
multiple paths if the apps design system spans multiple files.

## Implementation

The rule enforced using a custom `rust` check from
[Code Linting](code-linting.md), so it runs with `mix check` locally and in
CI. It is built to stay fast as the application grows:

- **The module is read once.** Before any file is scanned, the check reads
  the components module, collects every `def name(` whose name is lower case
  letters and digits, and builds one regular expression for all of them.
  `defp` does not count, and neither does a name like `button_link`, which
  cannot be a tag.
- **One pass per file.** The fast pass runs that one expression over the
  file. A match in a `.heex` file is confirmed on the spot. A match in an
  `.ex` file is only potential, because it may sit in a doc string or a
  comment.
- **Templates only, when it matters.** The slow pass runs only on the `.ex`
  files the fast pass flagged, and only over their `~H` templates. A
  `<button>` in a `@doc` is cleared. A `<button>` in a `~H` is confirmed.
- **The module itself is skipped.** It is where the raw tags belong.

### Configuration

```elixir
core_component_tags: [
  paths: ["lib/example_web/components/core_components.ex"]
]
```

`paths` lists the modules that make up the design system: the CoreComponents
module, an alternative module at its core, or several files. Every public
function across them is enforced, and a finding names the module that defines
the component. A tag defined in two of the modules is an error, so there is
never a question of which component the finding means.

### A finding and its fix

The generated theme toggle in the layout used raw buttons:

```
lib/example_web/components/layouts.ex:134: <button> may be a raw tag [core_component_tags, potential]
lib/example_web/components/layouts.ex:134: <button> is a raw tag, use <.button> from ExampleWeb.CoreComponents [core_component_tags, confirmed]
```

The fix is the dot. `class`, `phx-click` and `data-` attributes pass through
the component unchanged:

```heex
<.button
  class="flex p-2 cursor-pointer w-1/3"
  phx-click={JS.dispatch("phx:set-theme")}
  data-phx-theme="system"
>
  <.icon name="hero-computer-desktop-micro" class="size-4" />
</.button>
```

## Adopting this pattern

1. Adopt the [Code Linting](code-linting.md) pattern first. The check is one
   of the custom checks it runs.
2. Add a `core_component_tags` key to `.app_checks.exs` with the `paths` to the
   components modules, or leave it out if the module is the one
   `core_components.ex` under `lib`.
3. Run `mix app.checks` and read the findings. Convert each raw tag to its
   component.
4. To bring a new element under the rule, add the component to the module,
   such as `def p`, run the check, and convert what it finds. There is no
   list to update.
